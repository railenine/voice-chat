# Кандидат 0.2.3

Статус на 2026-11-08: подготовка в fix/sequential-audit-fixes, PR #10 остаётся
черновиком. Публикация, тег и переключение production пока не разрешены.
Production работает на прежнем коде 0.2.2 с выделенным Node 22.22.0.

## Подписанная сборка без публикации

В GitHub Actions открыть Build Desktop App (Tauri v2), нажать Run workflow и
выбрать fix/sequential-audit-fixes. Ручной запуск собирает production-кандидат,
подписывает portable и NSIS ключом из существующих GitHub Secrets, проверяет
подписи публичным ключом приложения. Тег не нужен. Релиз и backend не меняются.
Ключи не нужно передавать в чат или добавлять в репозиторий.

Результат в артефакте RVxis-Windows-x64: RVxis.exe (portable), совместимый
voice-chat.exe, NSIS, MSI, latest.json, подписи и release-candidate.json.
Отчёт содержит исходный коммит, версию, размеры, SHA-256 и результат проверки
подписей portable и NSIS. MSI здесь не является каналом автоматического
обновления; его подпись этим отчётом не подтверждается. Minisign обновлений
не заменяет Windows Authenticode.

Сборка прервётся при несовпадении версий, тестовой конфигурации, отсутствии
установщика нужной версии, неверной подписи или несовпадении хеша.
Публичные URL в latest.json относятся к будущему v0.2.3 и до публикации могут
возвращать 404. Этот артефакт ещё не подтверждает доставку через GitHub/CDN.
Исходные latest.json — шаблоны без подписей; их нельзя выдавать за готовые
манифесты обновления. Подписи и хеши генерируются только для собранных байтов.

## Что блокирует выпуск

1. Успешная подписанная сборка с реальным ключом проекта, сверка отчёта с
   нужным коммитом. Ранее ручные проверки updater использовали тестовые ключи.
2. Проверка перехода между версиями клиента и backend. Старый клиент 0.2.2
   не отправляет новый токен сессии для ICE HTTP, LiveKit token и загрузок.
   Нельзя обещать совместимость этих операций или отключать авторизацию
   ради неё. Новый клиент со старым backend тоже требует отдельной проверки:
   старое room-state не содержит sessionToken. Обычный staging с обеими новыми
   сторонами этого не проверяет. minClientVersion сейчас только поле ответа,
   само по себе оно не блокирует старые клиенты.
3. По результату матрицы совместимости — конкретный порядок публикации
   desktop, переключения backend и уведомления пользователей. До этого
   не сливать PR в main: push main запускает Deploy to VPS.
4. Отдельное согласование готового плана выпуска. Push тега v* запускает
   сборку и публикацию desktop. Обычный будущий tag-run пересобирает файлы;
   хеши ручной сборки не доказывают идентичность байтов tag-run.

Если требуется выпуск ровно проверенных файлов без пересборки, сначала
нужно реализовать продвижение артефакта по коммиту и хешам. Текущий workflow
этого не делает. Это решение нужно принять до публикации.

# Переход 0.2.2 → 0.2.3

Проверка 09.11.2026: legacy source 9f7e8be099c9e69691718fd70e029be7536317e3
и кандидат из HEAD. `npm run test:compatibility` архивирует оба коммита без .env,
ставит зависимости по каждому lock-файлу без install scripts, собирает frontend
и запускает отдельные backend на loopback. Результат — .test-tmp/compat-*/report.json.
В CI матрица обязательна перед загрузкой кандидата на VPS и Windows-сборкой.

| Клиент | Backend | Результат |
| --- | --- | --- |
| 0.2.2 | 0.2.2 | Голос, чат, файлы, ICE HTTP, LiveKit token, переподключение работают |
| 0.2.3 | 0.2.2 | Те же операции работают; токен отсутствует, фиктивный токен не сохраняется |
| 0.2.2 | 0.2.3 | Первичный голос/чат работают; файлы, ICE HTTP, LiveKit token получают 401; reconnect отклоняется |
| 0.2.3 | 0.2.3 | Проверенные операции работают с авторизацией сессии |

Дополнительно проверяются комнаты из старого и нового клиентов на каждом
backend. На новом backend старый участник по-прежнему несовместим с защищёнными
операциями и переподключением; это может нарушить и восстановление связи с ним
у нового участника. Нельзя считать успешный первый звонок полной совместимостью.
В отчёте отдельно записывается звук после обоих переподключений; проверяются
приращения RTP bytes и audio energy, а не только исторические ненулевые значения.
В эксперименте уже установленный P2P продолжал передавать звук даже при отказе
в повторном входе через WebSocket. Поэтому наличие звука тоже не подтверждает
восстановление signaling-сессии или работоспособность защищённых API.

При legacy room-state без sessionToken кандидат больше не сохраняет строку
undefined и не отправляет Bearer undefined. Неверные старые значения очищаются.
Новый backend продолжает требовать действующий серверный токен; исключения для
неавторизованного старого клиента не добавлены.

## Порядок выпуска

1. Подготовить подписанный desktop из коммита с исправлением токена. Подписанные
   файлы run42515045176 относятся к более раннему 7fa1bfc и эту правку не содержат.
   Тесты и подписи старого кандидата не подтверждают новый EXE автоматически.
2. Сначала выпустить и проверить новый desktop, сохранив backend 0.2.2.
   Проверка реального обновления опубликованного EXE 0.2.2 — отдельный этап;
   эта матрица её не заменяет.
3. Предупредить пользователей об обязательном обновлении desktop. Публичных
   метрик доли обновившихся клиентов пока нет: исходить из полного перехода
   без подтверждения нельзя. minClientVersion сейчас не принудительный барьер.
4. После согласованного перехода — отдельно активировать новый backend и web,
   прервав текущие звонки, проверить рабочий сайт и связь. Старые вкладки должны
   перезагрузить страницу. Push main автоматически запускает deploy, поэтому
   merge до завершения клиентского этапа недопустим.

Для этого порядка подготовлены ручные режимы build/verify/publish в desktop
workflow: публикация переносит проверенные артефакты по source SHA/run ID/ZIP
digest без пересборки и push main. Автопубликация по тегу отключена. Реальный
выпуск и native update ещё не проверены/не разрешены; сначала нужен свежий
build и read-only verify по RELEASE_PREPARATION.md.

## Границы проверки

Chromium с искусственным микрофоном, отдельными контекстами и реальным P2P RTP
по loopback. STUN/TURN отключены в браузерном test harness, внешние запросы
страниц блокируются. Проверены выдача JWT и привязка к peerId, но не передача
экрана через настоящий SFU. Тест не запускает native EXE и не проверяет глобальные
хоткеи, WebView2, updater, WAN/TURN, CDN или Windows Authenticode. Предыдущие ручные
проверки этих частей сохраняют свои границы и не подменяются этой матрицей.
